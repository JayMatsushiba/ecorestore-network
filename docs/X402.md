# Ecorestore Network — x402 API Payments

## 1. Purpose

x402 is how the project charges for API access.

It is an open payment standard that reuses the HTTP `402 Payment Required` status code:
a server answers an unpaid request with the payment terms it will accept, the client
pays, and retries. No checkout page, account or API key is involved, which is what makes
it usable by autonomous agents as well as people.

Hedera contributes its own payment scheme and a reference implementation to the x402
standard, settling in HBAR or HTS tokens.

**x402 is not settlement.** It pays for compute and access. It has no relationship to
the release of restoration capital, and the two must never be joined. §2 is the whole
point of this document.

### Status: demoted

Idea 0.3 §4.8 **demotes** x402 from the core component Idea 0.2 made it to an optional
one, and rules that **it must never become a prerequisite for the core verification or
settlement flow.**

Two reasons are given, and the second governs the design: metered per-request
verification actively creates the specification-search incentive that §3.7.1 exists to
close. §5 of this document is the coupling §4.8 requires to be stated explicitly rather
than left implicit.

---

## 2. Authority Boundary

The system now has two payment paths. They are different in kind and must stay
structurally separate.

| | Settlement | API payment |
|---|---|---|
| Network | Arc | Hedera |
| Asset | USDC | HBAR / HTS |
| Instrument | Restoration Deed escrow | x402 |
| Authorises | Release of restoration capital against verified outcome | One HTTP request |
| Decided by | Contract state and an authorized verification | Payment verification at the edge |

The separation is enforced by them being different networks with different accounts and
different keys. Keep it that way. Consolidating onto one chain for tidiness would remove
the structural guarantee and leave only convention.

### Critical invariant

**Paying for an API request must never trigger, influence or substitute for a milestone
settlement.**

An x402 payment buys the execution of a request. It does not buy an outcome, a verdict,
a quantity, or a release of funds. No path may exist from the payment layer to
`verifyMilestone()` or `releaseTranche()`.

This is the same invariant as `ARCHITECTURE.md` §2 applied to a second payment system:
the contract, not the payer, controls settlement.

---

## 3. Protocol shape

Three parties:

* the **client** — an application or agent making the request;
* the **resource server** — the monetised endpoint;
* the **facilitator** — an optional third party that verifies payment payloads and
  settles them on the resource server's behalf, so the server need not run chain
  infrastructure.

The exchange is an ordinary HTTP round trip: the resource server answers an unpaid
request with `402` and its accepted terms, the client returns a payment payload, the
server has it verified, and the request proceeds.

---

## 4. Hedera's scheme

Hedera's *exact* payment scheme uses partially signed transactions in which **the
facilitator pays the gas and submits the transaction**.

The consequence for this project is worth stating plainly: the resource server needs a
**receiving account, not a signing key**. The payment gateway can hold no private key at
all.

That matters because §7 of `DEPLOYMENT.md` places `VERIFIER_SEED` — the identity that
signs every verdict credential — inside a single, dependency-light container. A key-free
paywall keeps that isolation intact rather than introducing a second signing container
at the network edge.

---

## 5. Metered verification and specification search

This section is the coupling Idea 0.3 §4.8 requires to be recorded in the docs. **x402
and pre-registration are not independent features. Metering may not ship without the
mechanisms in §5.2.**

### 5.1 The conflict

Idea 0.3 §3.7.1 names the hazard precisely. The problem it was written to solve is
*"the control set … selected and the analysis run at verification time, by a service the
restorer pays per request"* — which is:

> a researcher-degrees-of-freedom problem with money attached: run the verification
> against several candidate control sets, several observation windows, several index
> choices, and submit the favourable one. Every number in the verdict stays honest; the
> estimator is still biased.

Per-request verification is the natural unit of sale for x402. It is also the natural
unit of specification search. Charging per run, naively implemented, monetises the exact
behaviour the scientific design exists to prevent — and does so while every individual
number remains truthful, which is what makes it hard to see.

### 5.2 What closes it

Three mechanisms, all already implemented:

1. **Pre-registration.** `analysisPlanHash` is committed at `createDeed()`, before any
   outcome is observable. The committed plan fixes the metric, the observation windows
   as dates, the control selection *rule*, the index and masking chain, the confidence
   level, the parallel-trend criterion and the ring geometry. A re-run cannot use a
   different specification, because the specification was fixed before the first run.
2. **Determinism.** `verify()` is a pure function of `(plan, evidence, runIndex)`.
   Identical inputs give a byte-identical result. Under a committed plan, re-running the
   same evidence returns the same answer — so buying a second run buys nothing.
3. **Run-count recording.** `recordVerificationRun()` emits `VerificationRunRecorded`
   before a verdict may be submitted, and `auditor/agent.ts` raises a `RUN_COUNT`
   anomaly — at `critical` severity — when recorded runs exceed submitted results,
   reporting *"possible specification search despite pre-registration"*. Runs are
   therefore visible history, not private trials.

### 5.3 The failure mode metering creates

The commercial pressure of a paid API is to offer cheap unrecorded runs — a "preview",
a "dry run", a free tier that does not touch the chain.

**That is the p-hacking channel.** An unrecorded run is a private trial: it defeats
mechanism 3 entirely while leaving 1 and 2 apparently intact, because a caller who can
vary the evidence window or re-run privately and only pay to record the favourable
result has reconstructed exactly the degrees of freedom §3.7.1 removed.

The rule that follows: **every verification sold is a recorded verification.** No
preview tier, no unrecorded evaluation, no off-chain rehearsal.

### 5.4 What must never be charged for

The assurance bundle, the verification result, the verdict credential, the analysis
plan, and anything else a third party needs in order to check a verdict already issued.

The project's claim is that a settlement is independently reproducible: take the
published result, canonicalise it, hash it, compare to the chain. Putting that evidence
behind a paywall would leave the claim true in principle and unfalsifiable in practice.
Auditability is the product. Charge for the run, never for the proof.

## 6. Placement in the architecture

x402 is edge middleware. It belongs in a gateway in front of the monetised endpoint, not
inside the verification path.

```text
client ──402──► gateway (x402)  ──►  verify (TS)  ──►  analysis (Python)
                    │                                   no keys
                    ▼                                   no egress
              facilitator                               not internet-facing
              (verify + settle on Hedera)
```

Constraints:

* the gateway holds a receiving account ID and no signing key (§4);
* `analysis` remains unreachable from the internet, as `DEPLOYMENT.md` §7.3 requires;
* nothing about a payment enters the request that reaches `verify`.

---

## 7. Determinism

A paid run and an unpaid run of the same verification must produce byte-identical
results.

Payment gates access; it does not touch the result. No payment attribute — amount,
payer, account, transaction ID, timestamp — may enter the canonical `VerificationResult`
or any document that is hashed into `resultHash`.

Admitting payment data into the hashed result would bind settlement evidence to
commercial terms and destroy third-party reproducibility: an auditor re-deriving the
hash would need the payment record, which is not theirs to have.

---

## 8. Hedera account separation

The project touches Hedera for three unrelated purposes:

1. Guardian policy execution (Guardian's own operator account);
2. ATS outcome-token issuance (the token treasury);
3. x402 receipts.

Use three separate accounts. The x402 receiving account must not be the Guardian
operator account or the token treasury. A compromise of a public-facing payment endpoint
must not reach the account that can issue outcome tokens.

---

## 9. Trust boundaries and dependencies

The facilitator is an external party in the payment path. It verifies payloads and
submits transactions, so it can fail, censor or misreport a payment.

It sits entirely outside the settlement path, so the blast radius is limited to API
access — a failed facilitator means requests are refused, not that a verdict is wrong or
that funds move incorrectly. It is nonetheless a named dependency, and whether the
project runs its own facilitator or relies on a public one is an operational decision to
be recorded, not assumed.

---

## 10. Milestone position

Idea 0.3 §9 places x402 at **M6**, and marks it optional even there: *"Optional x402
**with** pre-registration coupling."* `CLAUDE.md` and `ARCHITECTURE.md` §8 both put it
outside M1, and the Restoration Deed is not yet deployed to Arc Testnet.

It is also **third in the cut order** (§9): cut the globe, then Tier 2 UI views, then
x402, then ATS lifecycle depth, then the Subgraph. Idea 0.3 records the trade honestly —
demoting x402 costs addressable prize money on the Hedera AI & Agentic Payments track,
and it is demoted anyway.

The sequence is therefore: close M1, deliver the scientific core, decide whether the
verification tier runs live at all (`DEPLOYMENT.md` §5), and only then consider
monetising it — with §5.2 in place, never without. Monetising an endpoint also commits
the project to operating it.

---

## 11. Implementation state (2026-09-10)

Nothing in this document is implemented.

* No x402 gateway exists, in any form. No endpoint returns `402`.
* No Hedera account has been created for receipts, and no facilitator has been selected
  or contacted.
* The verification pipeline is not exposed as an API at all; it is a batch process whose
  output the application reads as static evidence.
* The container architecture this document assumes (`DEPLOYMENT.md` §7) is itself a
  proposal and has not been approved or built.
* x402 remains demoted and optional per Idea 0.3 §4.8. This document records how it
  would have to work if it ships; it is not a commitment that it will. The mechanisms
  §5.2 depends on — plan commitment, determinism, `VerificationRunRecorded` and the
  Auditor's `RUN_COUNT` anomaly — do exist and are exercised by the current test suite.
